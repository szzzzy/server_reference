# 服务器端算法链路说明（对外版）

> 面向未接触过本项目代码的读者。文中所有 `函数名()` 均为**服务器代码里真实存在的函数**，
> 每个都附一句话解释，看得懂它在链条里的角色，不需要去翻源码猜。
> 代码位置：`voice_server_full/`（server = 网络服务，engine = 三模型推理代码）。

---

## 0. 一句话总览

设备端（ESP32 Julia）WSS 认证后**持续上传**音频帧（新版固件已移除本地 WakeNet 唤醒词，
"说没说唤醒词/说没说完整/说什么"全部由服务器判断）；服务器完成
**听（唤醒词判定 + VAD 判起止）→ 识（ASR 转文本）→ 想（LLM 生成回答）→ 说（TTS 合成并下发）**，
全程用 4 个文本命令（`MIC_STOP` / `SPKS` / `SPKE` / `MIC_START`）+ 纯 PCM 音频与设备对齐状态机。

```
设备          WSS          server 侧算法链路
────────────────────────────────────────────────────────────────────
持续上传 PCM1 ──→ wss_adapter._handler() → engine.on_frame()
                  → RingBuffer(字节流缓冲)
                  → 待机态: capture_until_endpoint(唤醒参数) ← 听·唤醒
                      → recognize() 匹配"你好小科"(同音容错) ← 识·唤醒
                      → 命中: _speak_prompt 应答 + MIC_START(设备→LISTEN)
                  → 唤醒态: capture_until_endpoint()  ← 听
                          ←── MIC_STOP(文本帧, 设备→THINKING)
                  → board_serial_asr_test.recognize()               ← 识
                  → real_engine._answer_qa():
                       Transformers generate + TextIteratorStreamer   ← 想
                       _sentence_chunks() + submit_tts_segments()    ← 切句
                       tts_worker.py(子进程) CosyVoice2 合成          ← 说
                          ←── SPKS 24000 → PCM×N → SPKE → 回待机
```

## 1. 上行：接收音频帧

| 函数 | 作用（人话版） |
|---|---|
| `wss_adapter.WssAdapter._handler(ws)` | WSS 连接处理：二进制消息 = 一帧 PCM1；文本消息 = 设备命令（MIC_START 等，只记录）；FILE 推送另说 |
| `common.pcm1_parse(frame)` | 切一个 PCM1 帧：16 字节头（魔数 PCM1 / 序号 / 长度 / 板侧音量 / 校验和）+ 640 字节音频正文；解析通过才交给引擎 |
| `RealVoiceEngine.on_frame(pcm1, raw)` | 收到合法帧：统计帧数/丢帧计数，并把**原始帧字节**追加进 `RingBuffer`（缓冲） |
| `ring_buffer.RingBuffer` | 把 WSS 的"推帧"伪装成"串口字节流"（接口同 pyserial：`read`/`reset_input_buffer`），使下面所有串口时代函数原样复用；真实帧停止后自动补合成静音帧，VAD 的"说完"判定依然有效 |

> 修改点：无（协议原有）。本环节把"16B 头丢弃、只留 640B 正文"这件事封装在 `pcm1_parse` 与 `board_serial_asr_test.read_frame` 内部，引擎拿到的是纯音频样本。

## 1.5 线上唤醒（新版链路：设备端无本地唤醒词）

固件已移除本地 WakeNet（`wake_detector.c` 不再编译，无 WakeNet/AFE 符号，不打包 srmodels.bin），
WSS 认证后 **持续上传 PCM1**（16kHz/20ms/带 seq 与 dBFS；待机/夜间 UI/SPEAK 期间均不断流，
SPEAK 期间含扬声器回声）。服务器侧状态机（`server/real_engine.py`）：

- **待机态**（未唤醒，接通即进入）：用唤醒专用 VAD 参数（**灵敏**：背景+3dB / 起声 20ms /
  窗口 500ms / 尾静音 500ms / 段上限 8s —— 只探测"有人说话"，宁可多判候选 ASR 也不能漏掉
  唤醒词）判一段；**流式增量识别**（600ms 块粒度，`StreamingAsr`）：边说边识、命中即
  early-stop（`stop_event`），段末 `finish` 只补尾巴识别（≈0.06s，无需整段重跑）→ 归一化后
  与"唤醒词同音候选"匹配（内置"你好小科" + 逐字替换一个同音字的候选集合，如 科/柯/棵/颗/课
  ——实测 Paraformer 把"你好小科"识别成"你好小柯"）；未命中继续守听（不下发任何命令）。
  段上限 8s 是检测频率与"唤醒词不被截断"的平衡点（3s 会切掉词尾，实测"你好小"缺"科"）；
- **命中** → TTS 播唤醒应答（config `voice.real.wake.prompt`，默认"我在，请讲。"；文本勿含
  唤醒词，否则回声音频会自触发）→ **丢弃应答期间上行**（无 AEC，含扬声器回声，否则 MIC_START
  后的第一句会识别成应答内容）→ 下发 `MIC_START`（设备→LISTEN）→ 进入唤醒态；
- **唤醒态（持续对话，唤醒一次即可）**：一轮问答编排（VAD→MIC_STOP→ASR→LLM→TTS→SPKE）后
  **自动续听**（SPKE → MIC_START），**不再需要重复说唤醒词**；持续上传流中的静音段不作为
  轮次（不 MIC_STOP/不空轮）。**对话态 VAD 严格**（`voice.real.vad`：背景+5dB / 起声 120ms，
  环境声与低语不会被当成"问题"来回答；端点阈值保持 +3dB 防尾音截断）。唯一退出条件 =
  **空闲超时**（`timeout_seconds`，默认 60s，无"判了起始"的段即回待机，不发任何下行命令；
  设备侧 UI 由固件 5 分钟远场待机自愈）；
- **动态底噪启用时跳过开机静态校准**：校准窗口会消费持续上传流的开头音频（实测唤醒词前半段
  被校准窗口吃掉 → 只剩"小科"，且 3 次重试造成启动后约 24s 哑巴期）；bg_t 由估计器在每轮
  预语音段自学（初值 = config 默认），旧固件/未启用动态底噪时保留原校准行为。

配置（`config.json → voice.real.wake`）：`enabled`(默认 true)、`words`（默认仅["你好小科"]）、
`prompt`、`timeout_seconds`、`listen_seconds`、`endpoint_silence_ms`、`start_active_ms`、
`start_window_ms`。

**未实现（需 AEC）**：SPEAK 期间用户打断（设备已预留 EVT_INTERRUPT 链路，但服务器端区分
"扬声器回声"与"用户说话"需要回声消除，当前无 AEC，故打断判定暂缓）。

**半双工（防自问自答，无 AEC 的当前策略）**：SPEAK 期间麦克风持续上传并含扬声器回声；
服务器在 **SPKS→SPKE 播放期间不听**（主循环不消费上行），SPKE 后再丢弃 0.6s 回声余震
（`_playback_until`），播放期间积累的回声在回到主循环时一次性清空——否则设备把"刚播的
回答"录回去，服务器会再识别成新一轮问题（自问自答）。代价：播放期间用户不能抢话
（与"打断未实现"一致）。

**验证状态（2026-08-28）**：
- 固件侧（本地 WakeNet 切割 + WSS 认证后持续上传）：**已烧录测试通过**；
- 服务器侧：隔离端口全链路 5/5（唤醒应答 / 无唤醒词持续对话 / 回声免疫 / 超时二次唤醒）
  + 动态底噪真机 A/B（固定底噪 vs 动态 heal，turn3 2.16s 起始 / 4.92s 端点）；
- **唯一遗留待办**：① SPEAK 期间**打断**（需 AEC，见上"未实现"）；
  ② 展厅环境**真机声场复验**（唤醒距离 / 扬声器回声 / 噪声实景，非阻塞项——协议行为已
  对齐，建议按 `tools/servertest_wake.py` 素材在实地跑一轮对照）。

## 2. 听：VAD（语音起止判定）

**核心函数** `engine/board_serial_asr_test.capture_until_endpoint(ser, max_seconds, background_dbfs,
endpoint_silence_ms, threshold_above_bg, endpoint_threshold_above_bg, endpoint_active_penalty,
voice_start_ms, voice_start_window_ms)`

- 入参到出参：一边读帧一边判定，返回 `(整段音频 samples, 帧音量列表, 诊断字典)`；
  诊断字典里有 `speech_started`(检测到说话吗)、`endpoint_triggered`(判定说完吗)、
  `trailing_silence_ms`(尾静音)、`vad_threshold_dbfs`(用的阈值) 等，日志和状态页直接打印。
- 两块算法（纯能量，无模型）：
  1. **起始**：音量 > 背景+阈值 且连续活跃 ≥120ms 视作开始；录音起点回退 300ms 预卷（不切掉第一个字）；
  2. **端点**：说完后静音累计 ≥ 设定值（600ms）判"说完了"；活跃帧可抵扣静音（1ms 说话抵 4ms 静音），
     所以正常换气不会被切断，而孤立敲击声不会拖延端点；
  3. 兜底：超过 `max_seconds`(15s) 强制截断。

辅助函数：`rms_dbfs(samples)` 算音量(dBFS)；`capture_seconds(ser, seconds)` 采固定时长音频（开机背景校准用）；
`RealVoiceEngine._calibrate_background(stream, seconds)` 用前 2.5s 真实帧的 10% 分位估背景电平（3 次失败回退 -60dB）。

**动态底噪（可选，默认关闭）**：`engine/board_serial_asr_test.NoiseFloorTracker` —— 把"校准一次、
全程不变"的背景电平改成随环境变化的 `bg_t`（阈值 = `bg_t + 偏移`，每帧重算）：
- 双时间尺度：**fast 窗**（最近 1.5s 全部真实帧的 10% 分位，**不按电平过滤**——否则风扇/空调
  噪声（可比底噪高 15~20dB）永远进不了估计器，底噪就永远升不上去）负责环境变吵时快速上升
  （限 3dB/s）；**slow 窗**（最近 8s 低于 `bg_t+12dB` 的候选帧的 10% 分位）负责稳定估计与
  变安静时缓慢回落（限 0.5dB/s）；
- **防语音污染**：只有尚未判定"开始说话"的帧才进入估计器（即每轮预语音段），一旦判起始本轮
  冻结——语音结构性进不了估计器；上升还需连续 2 次确认（防单次事件误抬）；
- **静音快速回落（snap）**：分位显著低于当前估计（差 > 6dB，如关风机/人员散去）时直接重锚，
  避免 0.5dB/s 慢速回落导致"噪声刚停即轻声"漏检；仅在预语音段运行，以 8s 分位为锚。
- **会话级状态**：`RealVoiceEngine` 持有一个实例跨轮复用；校准结果只作 `bg_t` 初值，此后每轮
  预语音段（MIC_START 后、用户开口前）持续修正；
- **引擎级 heal（P2）**：一轮"判了起始但从未触发端点"（被持续高电平钉死，即底噪失效）→ 用该轮
  帧电平 10% 分位重锚 `bg_t`（钳制 [-80,-35]）；仅"空识别或活跃占比≈100%"的纯噪声轮才丢弃
  文本走空轮收尾，混合轮重锚后仍正常作答 —— 防突变噪声"每轮都坏"（仅 `dynamic_floor` 开启时
  生效）；
- **音频时钟**：估计器时间戳 = 帧数驱动（epoch + 样本数/sr），实时链路等价（帧按 50fps 到达），
  回放/回归确定可复现；
- 开关：`voice.real.vad.dynamic_floor.enabled`，默认 `false`；关闭时 `floor_tracker=None`，
  走原路径，行为与固定底噪完全一致。

> 修改点：`voice_start_ms`(120) 与 `voice_start_window_ms`(300) 原本**硬编码在函数里**，
> 现改为全部参数从 `config.json` 读取（VAD 参数表见 §7）；`endpoint_ms` 1000→600ms（快 0.4s）；
> 新增可选参数 `floor_tracker`（缺省 None = 旧行为）。

## 3. 协议点：MIC_STOP（本轮"说完了"的信号）

VAD 判"说完"的**同一时刻**（实测 2ms 内），引擎向设备回发独立文本帧 `MIC_STOP`：

- 这是本轮语音输入的结束标志，设备收后停传麦克风、UI 进 THINKING —— 必须发送；
- 位置：`real_engine._load_and_answer_loop()` 中 `capture_until_endpoint()` 返回后、`recognize()` 之前；
- 即使本轮无有效语音（<0.1s）也发送，设备不会卡在 LISTENING。

> 修改点：新增（协议适配）。

## 4. 识：ASR 语音转文字

**核心函数** `engine/board_serial_asr_test.recognize(model, samples)`：

- 输入一段 int16 音频，输出 `(完整文本, 首块出字耗时秒, 总耗时秒)`；
- 内部机制（无需调用方关心）：按 600ms 一块切，逐块调 FunASR `model.generate(..., cache=cache,
  is_final=...)`；`cache` 跨块传递模型"记忆"（同音字靠上下文校正），最后一块 `is_final=True`
  冲刷缓冲把剩余字吐全。
- 模型加载：`engine/asr_eval_core.load_paraformer(model, device)` 一次性加载（本地快照优先，
  离线可用），进程内常驻。

> 修改点：识别机制未动。仅在**识别结果为空**或**音频太短(<0.1s)**时处理方式改为"空轮收尾"（见 §6），
> 不再静默丢弃。

## 5. 想：LLM 生成回答

**核心函数** `RealVoiceEngine._answer_qa(turn, user_text, tokenizer, llm, streamer_cls,
sentence_chunks, queue, tts_dir, tts_base, result_csv, asr_seconds, input_wav, endpoint_wall)`
（一个函数干完一轮问答，三个并行体）：

| 并行体 | 干什么 |
|---|---|
| 生成线程 | `llm.generate(...)` 逐字产出，经 `TextIteratorStreamer` 管道流出（贪心解码，`max_new_tokens` 可配） |
| 切句线程 `submit_tts_segments()` | 迭代流式输出 → 逐句/分段 → 每段写一个 TTS 请求文件 → 放进段队列（不等上一段播完就合成下一段） |
| 主线程（播） | 从队列逐段 `_stream_tts_segment()` 下发到 WSS |

- 提示词拼装：`system_prompt`（通用助手版：2-3 短句/首句≤15 字/同音字容错/问候引导）
  + 最近 `history_turns`(2) 轮历史（存于 `RealVoiceEngine._history`，问后方记录、下轮注入）
  + 本轮用户文本；模板由 `tokenizer.apply_chat_template()` 完成。
- 计时：以 VAD 判定"说完了"为原点，记录 端点→首字、端点→首块音频、整轮 耗时（写入 CSV + 状态页）。

> 修改点：提示词通用化（原导游版删掉）、`max_new_tokens` 180→80、**新增多轮历史**。

## 6. 切句与分段（边说边播的粒度控制，本轮最多修改处）

### `RealVoiceEngine._sentence_chunks(streamer, fast_cut)`
把 LLM 流式输出切成"句"的生成器：
1. 遇 `。！？!?；; 换行` 切一句；
2. **首段快切** `fast_cut=12`：缓冲≥12 字遇逗号/顿号也切（LLM 首句往往很长，等整句 TTS 才开口就慢了）；
3. 48 字无标点保护（20~48 字逗号回退，否则硬切）；
4. 生成结束剩余即尾句。

### `submit_tts_segments()` 的分段缓冲（V5 式策略）
把切出的句子攒一攒再送 TTS：
- **首段：完整一句立即送**（不再等攒满 12/18 字——否则"你好。"这种短首句会被憋住）；
- 后续段：攒 40 字或 2 句再送（语气连贯）；
- **生成结束后残留缓冲强制提交**（关键修复：以前丢弃，症状就是"只播了第一句/末尾内容消失"）。

> 修改点（对应你遇到过的问题）：快切、首句即送、残留 flush 三处；
> 每段 = 一个 `request_<id>.json`（含文本/输出路径/流目录），交给 TTS 子进程。

## 7. 说：TTS 合成（独立子进程）

### 拉起：`engine/realtime_pipeline.start_tts_worker(config, run_dir)`
检查 5 个必需路径（TTS 环境 python / worker 脚本 / 模型目录 / 参考音频 / CosyVoice 源码）→
`subprocess.Popen` 拉起 → 等 `ready.json`（≤180s）→ 返回 `(进程, 队列目录)`。

### 合成：`engine/tts_worker.py main()`
单线程循环：
1. 扫队列 `request_*.json`（按名排序，取第一个）；
2. `CosyVoice2.inference_zero_shot(文本, 参考文本, 参考音频, stream=True)` —— 零样本音色克隆，
   边合成边 yield；
3. 每块张量(1×N, **24kHz**) → clamp → int16 → 原子写 `stream_dir/chunk_N.pcm`（N 从 0 起）；
4. 全部完成 → 拼装写完整 wav + 写 `response_<id>.json {ok, stream_chunks, audio_seconds, sample_rate, ...}`；
5. `shutdown` 指令退出；任何异常写 `{ok:false, error}`（不会死循环）；
   原子写 = 先写 `.tmp` 再改名（无锁文件 IPC 的一致性保证）。

> 修改点：参数来源改为本 config `tts` 段（不再依赖外部的"基础配置"文件）；
> 产物本就是纯 PCM16（无需 MP3/WAV 解码这一步，协议要求天然满足）。

## 8. 下发：SPKS → PCM → SPKE（→ MIC_START）

**核心函数** `RealVoiceEngine._stream_tts_segment(queue, request_id, stream_dir, start_board, end_board)`：

1. 轮询 `stream_dir/chunk_N.pcm`；首块到达先发文本 `SPKS 24000`（开播，必须早于一切 PCM，采样率=实际 24kHz）；
2. 每块拆 **≤1200B、偶数字节** 的二进制帧推送（纯 mono PCM16 LE，无任何头），
   并按 0.88 节奏（≈1.14×实时，保设备缓冲不欠载）；
3. `response_<id>.json` 出现且块数校验齐 → 本轮结束发 `SPKE`；
4. 跨段连续播：只首段发 SPKS、全部段播完统一 SPKE（段间不中断）；
5. 超时(180s)/异常：强制补发 SPKE 收尾。

收尾（`_answer_qa` 尾部）：SPKE 后若 `voice.mic_restart_after_answer=true`（**默认开**）→ 立即发
`MIC_START`，设备回 LISTENING 继续下一轮 → 形成多轮对话（第二轮起 LLM 带历史）。

**空轮收尾**（识别为空/无有效语音）：不做任何语义内容，但按协议完整收尾：
`SPKS 24000 → 0.12s 静音 PCM → SPKE → (多轮)MIC_START` —— 设备听到"无声的一轮"，绝不卡 THINKING。

> 修改点：新增 MIC_START（多轮）、空轮收尾、单轮异常保护（抛异常也补 SPKE、引擎线程常驻不崩）。

## 9. 一轮完整时序（实测 2026-08-27, 4B）

| 时刻 | 动作 |
|---|---|
| 0.00s | 设备 WSS 接入并 MIC_START；开始上传 PCM1×150 帧(3.0s@16kHz) |
| 3.00s | VAD 尾部静音 600ms 判定"说完了" |
| 3.00s+2ms | 服务器 → `MIC_STOP`（设备→THINKING） |
| 3.4s | ASR 出手："风十一度"(耗 0.34s) |
| 4.0s | LLM 首字(0.94s)；边生成边切句 |
| 6.4s | TTS 首块完成 → 服务器 → `SPKS 24000` |
| 6.4~7.5s | 服务器 → PCM×77 帧（≤1200B/帧，mono PCM16 @24kHz） |
| 7.5s | 服务器 → `SPKE` → `MIC_START`（继续下一轮） |
