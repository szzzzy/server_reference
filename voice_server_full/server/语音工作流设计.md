# 语音工作流设计 v2(服务器职责 + 待确认项;不含任何板卡行为假设)

> 适用范围:`voice_server_full/server/` 的 `voice.mode = "real"` 引擎(当前为 stub,本设计是其实现蓝图)。
> **原则**:服务器只负"收到什么、返回什么";板卡在做什么、什么时候传、传多少、
> 是否有触发/唤醒机制 —— **均以固件协议基线文档为准,未定义处一律列为待确认,不作预设。**

---

## 0. 各方立场(先划清)

**固件协议文档已写死的事实(服务器必须遵守)**:

| 事实 | 出处 |
|---|---|
| WSS 上行 binary 帧 = PCM1(16B 头:魔数/seq/字节数/dBFS×100/校验 + 音频,单帧 ≤1200B) | 协议 §4.2 |
| 下行文本命令:`MIC_START/MIC_STOP/MICS <bg>/MICW/SPKS <rate>/SPKV <n>/SPKE/SPKT/FILE_SEND <uri>` | 协议 §4.3 |
| 下行 binary = PCM16;`SPKS` 未先发则设备丢弃 | 协议 §4.3 |
| 鉴权:`Authorization: Bearer <token>`;保活 15s PING / 10s PONG / 5s 重连 | 协议 §4.1 |
| `BEGIN FILE…END` 文件推送序列(≤8 MiB、.wav、ERROR 表) | 协议 §4.2 |
| MQTT 控制面(O T A/音频素材/`vcmd`/`vstatus`)与本工作流并行,互不干扰 | 协议 §5 |

**服务器职责(本项目决定)**:

- 上行:解析 PCM1 → 攒一段音频 → VAD 端点 → 现有 ASR(Paraformer)→ 文本;
- 决策:是否需要回复、回复什么(规则见 §3,当前为待确认项);
- 下行:`SPKS <rate>` → 二进制 PCM 帧 → `SPKE`;文本命令透传/由会话逻辑决定;
- 落盘与指标:音频/文本/耗时写 runs/,与现有测试 CSV 风格一致。

**本设计明确不做预设(旧 V5 假设已移除)**:

| 旧假设 | 状态 |
|---|---|
| 板卡本地 120ms 能量检测、超背景 +5dB 触发 | ❌ 移除(固件协议只描述 `MICS <bg>` 的文档语义) |
| 触发上传含前 500ms 预录 | ❌ 移除 |
| 唤醒词"你好导游/小游小游/你好小游" | ❌ 移除(词表未定义) |
| 预合成固定提示音("我在,有什么需要帮助") | ❌ 移除(未定义) |
| 会话超时 120s、退出词表 | ❌ 移除(参数可配置,默认值不写死) |
| 重连后"重新校准背景"(设备侧行为) | ❌ 移除(设备行为未定义) |

## 1. 服务器侧数据流(只讲服务器)

```
WSS 上行 binary(PCM1)──► RingBuffer(兼容字节流)
                              │ 采集线程(复用现有 capture_until_endpoint)
                              ▼
                         一段音频 → ASR(recognize)→ 文本
                              │
                              ▼
                      §3 决策:要不要回复?
                              │ 要
                              ▼
                       Qwen3 流式 → sentence_chunks 分句
                              │
                              ▼ 逐句
                       tts_request → tts_worker(子进程)
                              │
                              ▼ 每句
                下行桥:SPKS <rate> → PCM 二进制帧 → SPKE
```

- 上行采样率 16k(协议文档 PCM1 语义为 16 kHz 20ms);
- 下行采样率 = TTS 模型采样率(以 tts_worker `response.sample_rate` 为准),`SPKS <rate>` 明示;
- WSS 断链/设备断开 → 服务器终止本会话任务,清 RingBuffer 与 LLM history(服务器侧行为)。

## 2. 字节流兼容层(RingBuffer,与 V5 无关的实现细节)

```
class RingBuffer:                       # 线程安全
    read(n, timeout) → bytes            # 阻塞直到凑满 n 字节(兼容 serial.read 语义)
    read1() → bytes                     # 单字节读(read_frame 逐字节扫魔数)
    reset_input_buffer()                # 清空
    flush() / is_open / close()         # 兼容属性
    append(pcm1_frame_bytes)            # WSS 帧原样塞入(16B 头 + payload)
```

- 塞入"原始 PCM1 帧字节"→ 现有 `read_frame()` 魔数扫描/校验/seq/dBFS 解析原逻辑工作;
- 容量上限 512 KB,超限丢最旧;
- 线程语义:WSS 异步任务 append,采集线程阻塞 read。

## 3. 决策规则(一问一答,已确认)

**业务形态:一问一答。没有唤醒词、没有对话状态机、没有角色提示词、没有开场/结束话术。**

| 决策点 | 已确认值 | 说明 |
|---|---|---|
| 触发规则 | 每段语音直接问答,`trigger_words: []` | 无唤醒词 |
| 对话状态 | **不设对话状态机**:每段音频 = 一问,答完即回待机 | 无 exit_words、无超时 |
| 系统提示词 | 空/最小中性(`system_prompt: ""`),不依赖提示词 | 不做导游/角色扮演;如需简短风格约束(如"请用中文简短回答")可后续配置 |
| 历史轮数 | `history_turns: 0`(每问独立回答,可配) | |
| 固定提示音 | 不需要(`greeting_text: ""`) | |
| 待机时板卡上传模式 | 未确认(MICS 触发 / MICW 持续)——**服务器两种都兼容**:有音频就答,没有就不做 | 不阻塞开发 |

**剩余唯一待确认项(不阻塞 R1–R4)**:板卡待机时是 `MICS` 触发上传还是 `MICW` 持续上传 → 影响第一条命令由谁发(服务器发 MICS/MICW / 设备默认),实现上做成配置。

## 4. 下行音频桥(tts_stream_to_wss)

- 发送顺序:`SPKS <rate>` → 二进制帧(≤1200B/帧,奇数长度去尾)→ `SPKE`;
- chunk 来源:tts_worker 的 `stream_dir/chunk_*.pcm`(既有流式机制,零新增合成逻辑);
- 帧节奏:WSS 背压即可,不做人为 sleep(设备播放缓冲行为以固件为准);
- 停止:response.json 的 `stream_chunks` 数达到即 `SPKE`;失败 → 记 error + `SPKE`。

## 6. 实施分阶段(不依赖上述待确认项的部分先做)

| 阶段 | 内容 | 验收(模拟器) |
|---|---|---|
| R1 | 引擎骨架 + RingBuffer + 采集/ASR 直连 | 语音流 → WAV 落盘 + 识别文本 + 指标 |
| R2 | Qwen3 流式 + 分句 + LLM 历史(默认应答) | 文本链打印/落 CSV |
| R3 | TTS + 下行桥 | 模拟器断言 SPKS/SPKE 顺序、下行帧计数 |
| R4 | 真机联调 | 需固件侧确认(证书信任/采样率支持/token) |
| R5 | 一问一答要素验证(`trigger_words=[]`、无提示词、无对话状态) | 模拟器:连续两问 → 两次独立回答(不携带上下文) |

> R1–R3 不涉及任何板卡行为假设;确认项只影响"什么时候应答/说什么/退出条件",不影响链路骨架。
